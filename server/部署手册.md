# 交换机信息查询 APP — 授权服务部署手册

适用系统：Rocky Linux 8 / Rocky Linux 9（同一套步骤，两版本通用）
运行环境：Python 3.11 + 纯标准库，无第三方依赖
部署形态：systemd 常驻服务，自签名证书 HTTPS

---

## 0. 前置确认

```bash
cat /etc/rocky-release          # 确认版本
ip -4 addr show | grep inet     # 确认服务器 IP
systemctl status firewalld      # 确认防火墙状态
getenforce                      # 确认 SELinux 状态
```

记下服务器公网 IP，后续用 `<服务器IP>` 表示。

## 2. 安装运行环境

```bash
dnf install -y python3.11 python3.11-pip openssl policycoreutils-python-utils tar
python3.11 -V
```

两条系统上的包名完全一致。**必须使用 `python3.11` 这个明确版本名**，不要用 `python3`（Rocky 8 是 3.6，Rocky 9 是 3.9，行为不同）。

> Rocky 8 如果提示找不到 python3.11，说明系统版本低于 8.8，先执行 `dnf update -y` 再试。

## 3. 建立目录与运行用户

```bash
useradd -r -s /sbin/nologin appsvc
mkdir -p /opt/switch-auth/{cert,data,backup,releases}
chown -R appsvc:appsvc /opt/switch-auth
chmod 750 /opt/switch-auth
```

目录结构：

```
/opt/switch-auth/
├── app.py              # 服务程序
├── config.json         # 配置（含密钥，权限 600）
├── cert/
│   ├── server.crt      # 自签证书（APP 内嵌这一份）
│   └── server.key      # 私钥（权限 600）
├── data/
│   └── app.db          # SQLite 用户库
├── releases/           # APP 发布包（后台「APP 版本发布」上传）
└── backup/             # 每日备份
```


## 5. 生成自签名证书（有效期 20 年，一次生成长期复用）

> **注意**：下面是示例，把 `39.107.26.67` 换成您服务器的真实 IP。
> **不要照抄尖括号**，`IP:<...>` 会被 openssl 判为非法 IP 并报 `bad ip address`。

```bash
cd /opt/switch-auth/cert && openssl req -x509 -newkey rsa:2048 -sha256 -days 7300 -nodes -keyout server.key -out server.crt -subj "/CN=39.107.26.67" -addext "subjectAltName=IP:39.107.26.67"
chown appsvc:appsvc server.key server.crt
chmod 600 server.key
chmod 644 server.crt
```

> 上面特意写成单行：多行写法依赖行尾 `\` 续行，手动复制粘贴时容易被吞掉，
> 会出现 `-keyout: command not found` 这类报错。

验证 SAN 是否正确写入：

```bash
openssl x509 -in server.crt -noout -text | grep -A1 "Subject Alternative Name"
# 期望输出：IP Address:39.107.26.67
```

若系统 openssl 不支持 `-addext`，改用配置文件方式：

```bash
cd /opt/switch-auth/cert
cat > san.cnf <<'EOF'
[req]
distinguished_name = dn
x509_extensions = v3_req
prompt = no

[dn]
CN = 39.107.26.67

[v3_req]
subjectAltName = IP:39.107.26.67
EOF

openssl req -x509 -newkey rsa:2048 -sha256 -days 7300 -nodes \
  -keyout server.key -out server.crt -config san.cnf
```

要点：

- `-days 7300` = 20 年，超出 Android 对证书有效期的常规限制要求，但自签证书不在系统信任链内、APP 内嵌校验，可用
- `subjectAltName` 里写服务器 IP，方便浏览器访问时比对
- **`server.crt` 要留存**，将来要放进 APP 的 `res/raw`。换服务器、升 Rocky 9 时**复用这张证书**，APP 就不用换
- 如果将来服务器 IP 变了，证书里的 SAN 不匹配只会让浏览器提示，APP 内嵌校验不受影响（但建议重新签发并同步更新 APP）

## 6. 准备配置文件

先生成两把密钥：

```bash
# APP 与服务端共享的响应签名密钥
python3.11 -c "import secrets;print(secrets.token_hex(32))"
```

复制这个值，后面要填两处：服务端 config.json 的 `app_secret`，以及 APP 源码里的同名常量。

```bash
cd /opt/switch-auth
cp config.example.json config.json
vi config.json
```

需要修改的字段：

| 字段 | 说明 |
|---|---|
| `listen_port` | 服务端口，默认 8443 |
| `app_secret` | 上面生成的那串 64 位十六进制 |
| `cert_file` / `key_file` | 默认已指向 `cert/server.crt`、`cert/server.key` |
| `token_days` | 登录令牌有效期，默认 7 天 |
| `admin_user` | 管理网页账号，默认 `admin` |
| `admin_pass_hash` | 先留空，下一步由命令写入 |

然后设置权限：

```bash
chown appsvc:appsvc config.json
chmod 600 config.json
```

初始化管理员密码（交互式输入，只存 PBKDF2 哈希，不存明文）：

```bash
python3.11 app.py --set-admin-pass
```

## 12. 账号、注册与审核

### 12.0 登录与退出管理后台

后台地址：`https://<服务器IP>:8443/admin`

打开后显示登录页，输入管理员账号 `admin` 和第 6 步设置的密码。登录成功后页面右上角有 **退出登录** 按钮。

- 会话保存在服务端内存，浏览器只持有随机会话 Cookie（HttpOnly、SameSite=Strict，启用 TLS 时带 Secure 标记）
- **空闲 30 分钟**自动失效；单次登录最长有效 12 小时
- 点「退出登录」立即失效；换浏览器或换电脑不会继承登录状态
- 服务重启后后台会话全部失效，需要重新登录（不影响 APP 用户）
- 同一 IP 5 分钟内输错 10 次会暂时拒绝登录
- 已彻底移除 HTTP Basic 认证，浏览器不会再缓存凭据

### 12.1 账号状态

每个账号有四种状态，只有「正常」可以使用 APP：

| 状态 | 产生方式 | APP 表现 |
|---|---|---|
| 待审核 | 用户自助注册（手动审核模式） | 禁止登录，提示"待管理员审核" |
| 正常 | 管理员添加 / 审核通过 / 自动通过 | 可正常使用 |
| 已拒绝 | 管理员审核拒绝 | 禁止登录，提示"已被拒绝" |
| 已禁用 | 管理员手动禁用 | 立即禁止，已登录会话下次校验即被拒绝 |

### 12.2 注册策略（三选一，网页后台可随时切换）

| 策略 | 效果 |
|---|---|
| 手动审核（默认） | 用户可在 APP 注册，注册后进入「待审核」，管理员通过后才能用 |
| 默认拒绝 | 关闭注册入口，只能由管理员手动添加账号 |
| 自动通过 | 用户注册即可使用，无需审核 |

后台位置：`https://<服务器IP>:8443/admin` → 「注册策略」卡片 → 选中 → 保存。

> 策略保存在 config.json 的 `register_mode`，可取值 `manual` / `auto_reject` / `auto_approve`。

### 12.3 审核注册

后台「待审核注册」卡片中，对待审核账号点 **通过** 或 **拒绝**。

### 12.4 手动添加用户

**方式一：管理网页**（推荐）→ 「新增账号」输入账号、密码 → 添加（直接为正常状态）。

**方式二：命令行**（管理页不可用时）：

```bash
cd /opt/switch-auth
sudo -u appsvc python3.11 app.py --add-user zhangsan
sudo -u appsvc python3.11 app.py --list-users
sudo -u appsvc python3.11 app.py --approve-user zhangsan
sudo -u appsvc python3.11 app.py --reject-user zhangsan
sudo -u appsvc python3.11 app.py --disable-user zhangsan
sudo -u appsvc python3.11 app.py --enable-user zhangsan
sudo -u appsvc python3.11 app.py --reset-password zhangsan
```

禁用或拒绝后，该用户**下一次启动 APP 或进入项目时立即被拒绝**，其已登录状态在下次校验时立即失效（无需等令牌过期）。

### 12.5 查看用户当前使用的版本

后台「账号列表」的 **当前版本** 列，显示该账号 APP 最近一次登录或校验时上报的版本（取自安装包 `versionName`）。

- APP 升级后**无需重新登录**，下一次校验（启动 APP 或进入项目页）时会自动更新为实际版本
- 显示「未上报」表示该账号使用的是不上报版本号的旧包（如本地认证包）
- 同一行的「在线令牌」是该账号当前有效登录令牌数量（每次登录签发一个，默认有效期 `token_days` 天，退出登录只撤销当前这一个）

## 13. 发送公告

后台「发布公告」卡片：

- **标题**：显示在 APP 公告列表顶部
- **目标**：默认「全体用户」，也可选择仅发给某个正常状态账号
- **内容**：最多 3000 字

APP 中公告以**常驻公告栏**方式展示，不再弹窗：

- 面向**全体用户**的公告：同时显示在**登录页**和一级页面，未登录也能看到
- 面向**指定用户**的公告：只在该用户登录后的一级页面显示
- 公告栏位于页面顶部，最多显示 3 条；首次出现时标题前带「【新】」

管理：

- **当前生效公告**卡片：查看所有正在下发的公告，点「取消公告」立即从 APP 中消失
- **公告列表**卡片：查看全部历史公告，可停用/启用/删除
- 取消与停用等效（`active=0`），历史记录保留可查

登录页公告来自公开接口 `GET /api/public/announcements`，无需令牌，只返回全体公告，不会泄露定向公告。

## 13.1 版本控制（禁止指定版本登录）

后台「版本控制」卡片为**添加模式**：

1. 在输入框填写要禁止登录的 APP 版本号（例如 `1.0`），点「添加到黑名单」
2. 下方表格立即列出该版本，每行右侧有「移出黑名单」按钮，可随时移出
3. 一次只添加一个版本；重复添加会提示「已在黑名单中」

- 黑名单为空表示不限制任何版本（表格显示「未设置黑名单，当前不限制任何版本」）
- 添加/移出后立即生效：被禁版本号登录返回「当前 APP 版本（x.y）无法使用，请安装最新版本」
- 已登录用户的会话在下一次授权校验时立即失效，无需等令牌过期
- 支持 `v1.1` 写法，保存时会自动规范为 `1.1`
- 格式错误（如 `1..2`）会在页面提示，不会写入

APP 登录与校验时会自动上报当前版本号（取自安装包 `versionName`），无需在 APP 内额外配置。

**关于旧版本**：早期 APP 包不会上报版本号。因此只要黑名单非空，**无法识别版本的旧包也会被拒绝**，否则旧包只要不上报版本号就能绕过封禁。黑名单为空时不限制任何版本。

**典型用法**：发布新版后，把旧版本号添加到黑名单，强制用户升级。

**排查封禁是否生效**：最直接的是看后台「账号列表」的 **当前版本** 列（见 12.5）。也可查数据库：

```bash
sqlite3 /opt/switch-auth/data/app.db \
  "SELECT u.username, t.client_version, datetime(t.issued_at,'unixepoch','localtime') FROM tokens t LEFT JOIN users u ON u.id=t.user_id ORDER BY t.issued_at DESC LIMIT 10;"
```

- `client_version` 为空：该登录来自不上报版本的旧包
- 显示 `1.1`：说明收到的是 1.1，封禁 1.0 对它无效，应改为封禁 1.1
- 后台「最近操作记录」中 `login_ok` 条目也会带有类似 `Android 15 v1.1` 的备注

## 13.2 APP 版本发布与应用内升级

后台「APP 版本发布」卡片用于上传新 APK，供用户点「APP 更新」时下载安装。

**上传步骤**

1. 用 Android Studio 打出**与线上同一签名**的 APK（`versionCode` 必须大于当前线上版本）
2. 后台选择 APK 文件，填写：
   - **序号**：`build.gradle` 里的 `versionCode`（如 `3`）
   - **版本名**：`build.gradle` 里的 `versionName`（如 `1.2`）
   - **更新说明**：显示在 APP 更新弹窗里，可留空
3. 点「上传并发布」，立即生效

**服务端行为**

- APK 保存到 `/opt/switch-auth/releases/app-<序号>.apk`，大小上限 200MB，只接受 `.apk`
- 自动计算 SHA256，APP 下载完成后会校验大小与 SHA256，不一致直接丢弃
- 序号重复会被拒绝，需先删除旧记录；发布记录可「停用/启用」「删除」
- 当前发布 = 所有启用的记录中序号最大的那个

**公开接口（无需令牌，被版本封禁的用户也能升级）**

| 地址 | 说明 |
|---|---|
| `/api/app/version` | 返回最新版本号、版本名、大小、SHA256、更新说明 |
| `/download/app.apk` | 下载最新发布版本的 APK |

**APP 行为**

- 登录页、项目列表页各有一个「APP 更新」按钮，**只在点击时检查，不自动检查、不自动下载**
- 有新版本 → 弹窗显示版本对比与更新说明，用户点「立即更新」才开始下载
- 下载完成校验通过后拉起系统安装界面；首次使用会要求允许「安装未知应用」
- 登录/校验被版本封禁时，登录页会直接弹出「立即更新」入口

**注意**

- 新旧 APK 必须是同一签名证书，否则系统拒绝覆盖安装
- `versionCode` 必须严格递增，否则 APP 不会提示更新
- APK 不进每日备份（体积大），迁移服务器时单独拷 `releases/` 目录，或到新服务器重新上传
- 后台「APP 版本发布」中的「删除」会同时删除服务器上的 APK 文件

**迁移服务器时用升级功能过渡**（IP 必须变化时）

1. 旧服务器**先不要关**，按新 IP 生成新证书、打新 APK（内含新地址与新证书）
2. 把新 APK 上传到**旧服务器**的「APP 版本发布」
3. 发公告通知用户点「APP 更新」完成升级
4. 确认大部分用户升级后，再关停旧服务器

完成以上后，从服务器取回：

APP 侧需要的信息只有三项：

## 16. 将来迁移到 Rocky 9 或其他服务器

因为已做到"证书复用 + 纯标准库 + 数据库独立文件"，迁移步骤固定：

```bash
# 老服务器
systemctl stop switch-auth
tar czf /tmp/migrate.tgz -C /opt/switch-auth data config.json cert releases

# 新服务器（先重复第 1~4、8~10 步装好环境）
scp /tmp/migrate.tgz root@<新IP>:/tmp/
tar xzf /tmp/migrate.tgz -C /opt/switch-auth
chown -R appsvc:appsvc /opt/switch-auth
chmod 600 /opt/switch-auth/config.json /opt/switch-auth/cert/server.key
systemctl enable --now switch-auth
```

迁移后分两种情况：

- **IP 不变**（推荐：把公网 IP 转成弹性公网 IP，迁移时解绑再绑到新实例）：证书、APP 均不用改
- **IP 变了**（当前只有固定 IP 时）：证书 SAN 绑定的是 IP，必须按新 IP 重新生成证书，并更新 APP 的服务器地址与内置证书后重新打包。用 13.2 的「旧服务器保活 + 应用内升级」过渡，避免用户手工重装

> Rocky 官方不把 8→9 原地升级列为受支持路径，建议新装系统 + 上面这套数据迁移，风险最低。

## 17. 常见故障排查

| 现象 | 排查方向 |
|---|---|
| 启动时报 `PermissionError: ... config.json` | 文件属主是 root。`chown -R appsvc:appsvc /opt/switch-auth && chmod 600 /opt/switch-auth/config.json`（每次用 root 改过配置都要重做） |
| 服务起不来 | `journalctl -u switch-auth -n 50`；多半是 config.json 权限或证书路径错误 |
| 外网访问不了 | 云安全组是否放行、`firewall-cmd --list-ports`、`ss -lntp \| grep 8443` |
| 浏览器证书警告 | 自签证书的正常现象，手动信任即可，APP 内嵌校验不受影响 |
| APP 提示"授权校验失败" | 服务端 `app_secret` 与 APP 内常量是否一致；服务器时间是否准确 |
| APP 提示"无法连接授权服务器" | 用 `curl -k https://<IP>:8443/api/ping` 从手机网络侧测试 |
| 时间校验失败 | `timedatectl status`、`chronyc tracking`，确保时钟同步 |
| 管理员密码忘了 | 删除 config.json 中 `admin_pass_hash` 后重新执行 `--set-admin-pass` |
| 打开后台仍直接进管理页、看不到登录框 | 浏览器残留了旧版 Basic 凭据或旧 Cookie。清除该站点 Cookie（或关闭浏览器）后重开；服务端已忽略 Basic 头 |
| 后台突然要求重新登录 | 空闲超过 30 分钟、登录超过 12 小时，或服务刚重启，均属正常 |
| 误停用自己 | 用另一个管理员账号在网页启用；或 `sqlite3 /opt/switch-auth/data/app.db "UPDATE users SET status='active' WHERE username='xxx';"` |
| 发不出公告 / 公告列表为空 | 确认点的是「发布公告」的提交按钮；发布后在「当前生效公告」卡片查看；被停用或取消的公告不再显示在生效区 |
| 登录页看不到公告 | 只有「全体用户」公告会出现在登录页，定向公告仅在登录后显示；确认公告为生效状态 |
| APP 全部用户被拒绝，提示版本停用 | 「版本控制」黑名单中包含当前版本，或客户端未上报版本号（旧包）。在表格中把该版本「移出黑名单」清空，或让用户安装最新版 APP |
| 已封禁某版本但仍能登录 | 先确认手机安装包的实际版本（系统「应用信息」查看）；旧包不上报版本号，服务端只能看到空值。用 `tokens` 表的 `client_version` 核对服务端实际收到的版本 |
| 改完 config.json 后服务异常 | 配置文件属主/权限要恢复：`chown appsvc:appsvc /opt/switch-auth/config.json && chmod 600 /opt/switch-auth/config.json`，再 `systemctl restart switch-auth` |
| 后台上传 APK 失败 / 页面提示上传失败 | 确认文件是 `.apk`、小于 200MB；目录属主必须是 appsvc（`ls -l /opt/switch-auth/releases`）；失败时看 `journalctl -u switch-auth -n 50` |
| APP 点「APP 更新」提示尚未发布 | 后台「APP 版本发布」还没有启用记录，先上传 APK |
| `/download/app.apk` 返回 404 | 当前没有启用的发布记录，或 APK 文件被删除。到后台上传/启用对应版本 |
| APP 下载完成但安装失败 | 新旧 APK 签名不一致（必须同一签名证书），或未允许「安装未知应用」 |
| APP 不提示有新版本 | 上传的「序号」不大于手机上的 versionCode。核对 `build.gradle` 与后台填写值 |
